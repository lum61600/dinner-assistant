# 聚餐選店助手

一頁式的部門聚餐投票工具。福委設定日期和餐廳，同事點連結投票，票數自動統計，最後一鍵產生公告。

**線上網址**：https://qiyi-studio.github.io/dinner-assistant/

---

## 這是什麼、解決什麼問題

客資部每兩個月要辦一次部門聚餐，由 Tobey、婧菱、Nana 三個人輪流當福委。這個工具就是把整個流程搬到一個網頁上。

**原本的做法是把投票彙整在一份共用表格裡**，福委開好日期和店家，大家自己去填。問題是表格不會提醒任何人——沒有截止日在眼前，也看不出自己填了沒、還有誰沒填，常常拖到最後福委才發現少了兩三票，只好一個一個去問。

統計也全靠人工。票是填進去了，但誰投哪天、哪家店最高、幾個人攜伴、總人數乘以 1000 是多少，還是得福委盯著格子自己算，算完再整理成公告貼出來。人不多，卻每輪都要重來一次。

**另一個很花時間的是選店**。輪到自己當福委，最累的不是統計，是「要選哪四家」。打開 Google 地圖漫無目的地滑，看到店名也不知道適不適合十個人吃，有沒有包廂、預算合不合、評價好不好，全都得一家一家開分頁查，光備料就耗掉一個晚上。

還有規則留不住的問題。每人 1000 含 10% 服務費、超支找親親、晚班要交 0501 公出假單、12 月停辦——這些散在各處靠口耳相傳，三個福委各有各的做法，也沒人記得上次到底去了哪家店。

所以這個工具要做四件事：**投票狀態一目了然、票數自動統計、選店有現成的起點、規則和紀錄固定在同一個地方。**

## 怎麼用

**要準備的東西**：一個瀏覽器。就這樣。同事不用註冊、不用安裝、不用登入。

### 福委

1. 開 https://qiyi-studio.github.io/dinner-assistant/ （**不要帶 `?s=`**，乾淨的網址才是開新一輪）
2. 選自己是誰（Tobey → 婧菱 → Nana 輪值）
3. 訂投票截止日，填四個候選日期
4. 設定四間餐廳，有三種找法：
   - 三顆搜尋捷徑，跳到 Google 地圖／推薦文／部落格食記
   - `🎲 店家清單抽 4 間`：從部門自己維護的常去清單隨機抽
   - `🗺 從地圖抓 4 間`：直接撈該地區地圖上的餐廳
5. 按**發布投票**，網址會自動長出 `?s=xxxxxxxx`
6. 按右上角**複製投票連結**，貼到群組

### 同事

點連結 → 選自己的名字 → 勾可出席的日期（可複選）→ 選餐廳（最多兩間）→ 要帶人就打勾 → 送出。隨時可以回來改票。

### 開票

票數表是「人 × 選項」的矩陣，誰投了什麼一目了然，最高票整欄標示。捲到最下面的「最後結果」，日期和地點會自動預選最高票，確認後按產生，就有一列公告可以存成圖片貼出去。

**下一輪**：再開一次乾淨網址就好，舊連結永遠有效，隨時能回去查上次去哪。

## 架構與檔案說明

```
dinner-assistant/
├── index.html    ← 整個 App，HTML + CSS + JS 全在裡面
└── README.md     ← 這份
```

真的就兩個檔案。沒有 build、沒有 npm install、沒有 node_modules。

`index.html` 內部的結構：

- **設定畫面**（01 福委 / 02 日期 / 03 餐廳）與**投票畫面**（01 你是誰 ~ 06 最後結果）是同一頁，靠 `S.published` 切換
- 所有狀態集中在一個 `S` 物件裡（福委、日期、餐廳、店家清單、每個人的票、最後結果）
- 這整包 `S` 以單一 JSON 存進 Supabase 的一列，發布時產生的 session id 就是那列的主鍵，也寫在網址的 `?s=` 上
- 送票前會先讀最新資料再合併寫回，避免兩個人同時投把對方蓋掉
- 每 15 秒自動同步一次

## 用了哪些技術、為什麼選它

### 純 HTML/CSS/JS，不用框架

一個五人用的投票頁，用 React 要先裝環境、跑打包，改個字還得重新 build。單一檔案的好處是任何人打開就能改，丟到哪都能跑，十年後也不會因為某個套件停止維護就掛掉。

### Supabase 當資料庫

一開始其實不是用它。原本這頁是在 Claude 環境裡跑，票存在它提供的共用儲存，多人投票沒問題——但**一放上 GitHub Pages 就全壞了**，那個儲存離開 Claude 就不存在，每個人開網址都是空白的一份，重整就消失。要有一條能貼進群組的網址，就非得有真的資料庫不可。

選 Supabase 而不是 Google Apps Script，是因為我們既有的會議記錄工具已經在用 Supabase，同一套經驗直接複用；而且它的 REST API 可以直接在前端 fetch，不用另外寫後端。

### GitHub Pages 託管

免費、沒有伺服器要顧、上傳檔案就自動部署。

### OpenStreetMap 找店（Nominatim + Overpass）

免費、不用金鑰、不用綁信用卡。缺點在下面「已知限制」。

### Canvas 手繪匯出圖片

沒用 html2canvas 之類的套件，因為那要載入外部 JS，多一個會壞掉的環節。直接用 Canvas 畫，程式碼多一點但零依賴。

## 中途踩過的坑

### 自動推薦餐廳失敗，整個功能重做了兩次

最早想讓程式自動查「附近熱門四間店」，第一版接 AI 搜尋，按下去只回 `Failed to fetch`——預覽環境擋掉所有對外連線，而且就算通了，部署到 GitHub Pages 後那個 API 也用不了。第二版改接 OpenStreetMap 的 Overpass API，一樣被預覽環境擋。最後拆成兩條路：**離線的**「店家清單抽 4 間」（自己維護的清單，任何環境都能用）＋**連線的**「從地圖抓 4 間」（部署後才會動）。教訓是**會對外連線的功能，一定要在真的網站上測，不能在預覽裡測**。

### 日曆點不開

原本用瀏覽器內建的日期欄位，只能點右邊那個小圖示才會跳日曆，很難按。試著用程式在點整格時叫出日曆，結果被瀏覽器擋下——網頁被放在跨來源的框架裡時，這個動作不被允許。最後**自己寫了一個日曆彈窗**，順便解決各家瀏覽器外觀不一致的問題。

### 票數用「正」字記，看起來很酷但沒人要

統計原本設計成用毛筆感的「正」字堆疊來數票，五筆一個正。做出來很有味道，但實際看不如直接寫數字快，後來改成大字數字，最後又整個改成試算表那種矩陣表格，因為「想知道誰投了什麼」比「總共幾票」更重要。

### 介面改過一輪風格

第一版是紙本單據風（米黃紙張、朱紅印章、襯線字），做完覺得太重，改成現在的白底卡片＋單一綠色強調的現代風。

### 星等做不出來

本來想讓抓回來的店直接照 Google 星等排序。查了才知道 OpenStreetMap 只有圖資沒有評價，這件事從根本上做不到。要星等就得接 Google Places API，而那要開 Google Cloud 專案並**綁定信用卡**——雖然免費額度絕對用不完，但為了一年幾十次查詢綁卡不划算，先擱著。

### 上傳到 GitHub 一直不生效

明明改好了網站卻沒變，原因是下載時檔名變成 `index (1).html`，等於多傳了一個新檔而不是覆蓋原本的。另外拖檔案進去之後**要捲到頁面最底部按 Commit changes**，只拖不按等於沒傳。

## 設定與金鑰怎麼準備

如果要自己開一份獨立的（例如換部門用），照這個順序：

**1. 建 Supabase 專案**

到 supabase.com 新增專案，Region 選 Northeast Asia (Tokyo)，資料庫密碼產生後自己存好。

**2. 建表**

左側 SQL Editor 貼上這段按 Run：

```sql
create table public.dinner_sessions (
  id text primary key,
  data jsonb not null,
  updated_at timestamptz not null default now()
);

alter table public.dinner_sessions enable row level security;

create policy "read"   on public.dinner_sessions for select using (true);
create policy "insert" on public.dinner_sessions for insert with check (true);
create policy "update" on public.dinner_sessions for update using (true) with check (true);
```

**3. 拿兩個值**

- **Project URL**：Settings → Integrations → Data API 頁面最上方，或直接看 dashboard 網址列 `project/` 後面那串，組成 `https://那串.supabase.co`
- **Publishable key**：Settings → API Keys，`sb_publishable_` 開頭那個

**4. 填進 `index.html`**

搜尋 `SUPA_URL`，在 script 開頭：

```js
const SUPA_URL = 'https://你的專案代號.supabase.co';
const SUPA_KEY = 'sb_publishable_你的金鑰';
const TABLE    = 'dinner_sessions';
```

用的是 **Publishable key**，這種金鑰設計上就是要公開在前端的，寫進 HTML 沒問題。**絕對不要換成 Secret key**，那個外洩等於資料庫整個被打開。

**5. 上傳到 GitHub Pages**

檔名必須是 `index.html`，Settings → Pages → Deploy from a branch → main → / (root)。

## 已知限制

**資料庫閒置會自動睡著**
Supabase 免費方案大約一週沒人用就會暫停。我們單數月才聚餐一次，幾乎每輪都會遇到。程式偵測到會直接顯示「請福委登入 Supabase 按 Restore，等一分鐘再重新整理」，不會出現看不懂的錯誤訊息。不想再管這件事的話，把它搬到我們已經在付費的那個 Supabase 專案就永遠不會暗停。

**知道網址就能讀寫**
資料庫權限完全開放，沒有帳號密碼。五個人內部用剛好，但別把連結貼到公開場合。

**沒有星等**
如上所述，OSM 沒有評價資料。每張餐廳卡片有「去 Google 看」按鈕，手動查一下填進去即可。

**地圖抓回來的店要人工確認**
OSM 由網友維護，可能撈到早餐店或已經歇業的店。地址自動查詢有時也只查得到路名沒有門牌，樓層要自己補。

**建議名單不保證有分店**
「店家清單抽 4 間」在自訂清單不夠時會用內建的連鎖店名單補（瓦城、這一鍋、燒肉眾那些），那是通用清單，不保證每個地區都有分店。

**投票截止後不會鎖定**
截止日只是顯示提醒，過期還是可以改票。

**沒有歷史紀錄頁**
每輪的連結都還在，但要自己留著。想查「前三次去了哪」目前得一條一條開。

**同時編輯是後蓋前**
兩人同一秒送出時，後送出的那筆會覆蓋。五人規模遇不到，沒有特別處理。
